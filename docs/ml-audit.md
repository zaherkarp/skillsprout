## 1. Scoring Pipeline Map

### 1.1 Input Layer

User input consists of skill ratings on a 0-4 integer scale, keyed by O\*NET skill element IDs (e.g., `2.B.1.a`). Ratings are submitted via `POST /api/v1/user/{user_id}/skills/ratings` and persisted in the `user_skill_rating` table with a `(user_id, element_id)` unique constraint.

| Rating | Label        | Capability Scalar |
|--------|--------------|-------------------|
| 0      | None         | 0.00              |
| 1      | Basic        | 0.25              |
| 2      | Intermediate | 0.50              |
| 3      | Advanced     | 0.75              |
| 4      | Expert       | 1.00              |

Source: `RATING_TO_CAPABILITY` dict in `app/ml/scoring.py`, lines 16-22.

### 1.2 BaselineScorer (Model v1) -- `app/ml/scoring.py`

The deterministic baseline model computes two primary metrics and derives a bucket assignment.

#### match\_score (0-100)

```
weight_i = importance_i / sum(all importances)
match_score = 100 * SUM(weight_i * capability_i)
```

- If `total_importance == 0`, falls back to equal weights (`1.0` per skill).
- Unrated skills default to rating 0 (capability 0.0) -- there is no explicit missing-data sentinel.

#### gap\_severity (0-100)

```
gap_severity = 100 * SUM(weight_i for all skills where capability_i <= 0.25)
```

A skill is considered a "gap" when the user's capability is 0.25 or below (ratings 0 or 1). The gap severity is the sum of normalized importance weights for those gap skills.

#### Bucket Assignment

Evaluated in order; first match wins:

| Bucket        | Condition                                                          |
|---------------|--------------------------------------------------------------------|
| `ready_now`   | `match_score >= 75.0` **AND** `gap_severity <= 25.0`              |
| `trainable`   | `match_score` in `[50.0, 74.0]` **OR** `gap_severity` in `[26.0, 55.0]` |
| `long_reskill` | Everything else                                                   |

All six threshold values are configurable via environment variables through `app/core/config.py`:

| Setting                      | Default |
|------------------------------|---------|
| `ready_now_match_threshold`  | 75.0    |
| `ready_now_gap_threshold`    | 25.0    |
| `trainable_match_min`        | 50.0    |
| `trainable_match_max`        | 74.0    |
| `trainable_gap_min`          | 26.0    |
| `trainable_gap_max`          | 55.0    |

#### Training Suggestions

Generated by `_generate_training_suggestion()` based on bucket and `target_job_zone`:

| Bucket        | Job Zone | Suggestion Theme                                         |
|---------------|----------|----------------------------------------------------------|
| `ready_now`   | any      | "Apply now, refresh with online courses"                 |
| `trainable`   | 1-2      | Certificate / apprenticeship (3-12 months)               |
| `trainable`   | 3        | Bootcamp / certificate + portfolio (3-18 months)         |
| `trainable`   | 4-5      | Associate degree / extended bootcamp (1-2 years)         |
| `long_reskill` | 1-2     | Vocational training / extended apprenticeship (1-2 years)|
| `long_reskill` | 3       | Associate degree / extended bootcamp (1-3 years)         |
| `long_reskill` | 4-5     | Bachelor's degree / multi-year program (2-4 years)       |

#### Output Metadata

Each `OccupationScore` includes a metadata dict with:
- `total_skills`: count of occupation skills
- `skills_with_gaps`: count of gap skills
- `current_job_zone`: user's current job zone (if known)
- `target_job_zone`: target occupation job zone
- `job_zone_diff`: `target - current` (or `None` if either is missing)

Top 10 skill gaps are returned, sorted by descending normalized importance weight.

### 1.3 CalibrationModel (Model v2) -- `app/ml/calibration.py`

A learned calibration layer that predicts `P(success)` for `(user, occupation)` pairs.

#### Feature Vector (9 features)

| #  | Feature              | Source                              |
|----|----------------------|-------------------------------------|
| 1  | `match_score`        | Baseline scorer output              |
| 2  | `gap_severity`       | Baseline scorer output              |
| 3  | `job_zone_diff`      | `target_job_zone - current_job_zone`|
| 4  | `target_job_zone`    | Occupation metadata                 |
| 5  | `num_missing_skills` | Count of gap skills                 |
| 6  | `sum_missing_weights`| Sum of normalized weights for gaps  |
| 7  | `mean_rating`        | Mean of user ratings                |
| 8  | `rating_variance`    | Variance of user ratings            |
| 9  | `num_rated_skills`   | Count of rated skills               |

#### Architecture

- **Algorithm:** `sklearn.linear_model.LogisticRegression`
- **Preprocessing:** `sklearn.preprocessing.StandardScaler` (fit on training data)
- **Class balancing:** `class_weight="balanced"`
- **Max iterations:** 1000
- **Train/test split:** 80/20 with stratification
- **Random seed:** 42

#### Training Pipeline

1. Feedback records are queried from `user_feedback` joined with `recommendation_event` and `recommended_occupation`.
2. Only actionable feedback is used: `HIDE`, `APPLY`, `INTERVIEW`, `OFFER`.
3. Labels: `APPLY/INTERVIEW/OFFER -> 1` (positive), `HIDE -> 0` (negative).
4. Minimum 50 samples required (`model_training_min_samples` setting).
5. Model is serialized via `joblib` and registered in the `model_registry` table.
6. Training is triggered via the `train_calibration_model_task` Celery task.

#### Prediction

Outputs a `CalibrationPrediction` with:
- `predicted_probability`: raw P(success) from logistic regression
- `calibrated_score`: `probability * 100` (0-100 scale)
- `model_version`: version string

#### Exploration Policy

An epsilon-greedy `ExplorationPolicy` class exists (`epsilon` default 0.1) that selects items near the middle of a ranked list for exploration. This is defined but **not currently wired into the recommendation endpoint**.

### 1.4 Data Ingestion -- O\*NET Client (`app/services/onet_client.py`)

| Client          | Mode       | Occupations | Notes                              |
|-----------------|------------|-------------|------------------------------------|
| `ONetClient`    | Live       | Any         | HTTP Basic auth, tenacity retries (3 attempts, exponential backoff) |
| `MockONetClient`| Demo       | 3 hardcoded | 15-1252.00, 15-1299.08, 15-1244.00 |

- Demo mode activates when `demo_mode=True` **or** O\*NET credentials are absent (`is_demo_mode` property).
- Skills are parsed from the O\*NET API response structure: `element.score[].scale.name` is matched against "importance" and "level".
- Fetched data is cached in the `occupation`, `skill`, and `occupation_skill` tables.
- Cache warming is performed by the `warm_occupation_cache` Celery task.

### 1.5 Recommendation Endpoint Flow -- `POST /api/v1/user/{user_id}/recommendations`

```
User Request
    |
    v
Verify user exists (404 if not)
    |
    v
Load active current occupation (400 if none)
    |
    v
Load user skill ratings (400 if empty)
    |
    v
Fetch ALL cached occupations with skills via joinedload (503 if none)
    |
    v
Score each occupation (excluding current) with BaselineScorer
    |
    v
Create RecommendationEvent record
    |
    v
Group scored occupations into buckets, sort by match_score descending
    |
    v
Persist RecommendedOccupation records (limit_per_bucket applied)
    |
    v
Return bucketed response with decision guidance
```

**Observations:**
- All cached occupations are loaded into memory and scored, regardless of count.
- The calibration model (v2) is referenced in `RecommendationRequest.use_calibration` but **the endpoint always uses the baseline scorer** -- calibration is not actually applied to rerank results.
- Top gaps stored in `score_json` are truncated to 5 (different from the scorer's 10).
- `gap_weight` is omitted from the persisted `score_json.top_gaps` entries.

## 2. Feedback Loop Inventory

### 2.1 Action Types

Defined as `ActionType` enum in `app/models/models.py`:

| Action      | Enum Value    | Used in Training | Signal Interpretation     |
|-------------|---------------|------------------|---------------------------|
| `CLICK`     | `"click"`     | No (ignored)     | Ambiguous -- interest or browsing |
| `SAVE`      | `"save"`      | No (ignored)     | Ambiguous -- bookmarking  |
| `HIDE`      | `"hide"`      | Yes (label=0)    | Clear negative signal     |
| `APPLY`     | `"apply"`     | Yes (label=1)    | Weak positive signal      |
| `INTERVIEW` | `"interview"` | Yes (label=1)    | Strong positive signal    |
| `OFFER`     | `"offer"`     | Yes (label=1)    | Strong positive signal    |

### 2.2 Capture Path

1. User submits feedback via `POST /api/v1/feedback` (`UserFeedbackRequest` schema).
2. Endpoint validates the `event_id` exists in `recommendation_event`.
3. Looks up the `recommended_occupation` record for the `(event_id, target_onet_code)` pair.
4. Creates a `UserFeedback` row with `action_type`, `action_at`, and optional `metadata_json`.
5. **Write is synchronous** -- the feedback is committed to the database within the request handler before the response is returned.

### 2.3 Training Data Extraction (`app/tasks/tasks.py`)

The `train_calibration_model_task` Celery task:

1. Queries `user_feedback` joined with `recommendation_event` and `recommended_occupation`.
2. Filters to `HIDE`, `APPLY`, `INTERVIEW`, `OFFER` actions only.
3. Extracts features from the stored `score_json` on each `recommended_occupation`.
4. **Three features are hardcoded placeholders** (lines 225-227):
   - `mean_rating = 2.0`
   - `rating_variance = 1.0`
   - `num_rated_skills = 10`
5. `sum_missing_weights` is computed from `top_gaps[].gap_weight`, but `gap_weight` is **not stored** in `score_json` (see Section 1.5), so it always sums to 0.

### 2.4 Signal Quality Assessment

| Signal    | Strength | Latency            | Volume Expectation |
|-----------|----------|--------------------|--------------------|
| CLICK     | Weak     | Immediate          | High               |
| SAVE      | Weak     | Immediate          | Medium             |
| HIDE      | Moderate | Immediate          | Medium             |
| APPLY     | Moderate | Hours to days      | Low                |
| INTERVIEW | Strong   | Days to weeks      | Very low           |
| OFFER     | Strong   | Weeks to months    | Very low           |

**Key concern:** The strongest positive signals (INTERVIEW, OFFER) have the longest latency and lowest volume. This creates a class imbalance heavily skewed toward HIDE as the dominant training signal. The `class_weight="balanced"` setting in logistic regression partially mitigates this, but the label distribution is likely still problematic at low sample sizes.

## 3. Cold Start Analysis

### 3.1 User Cold Start

| Condition                  | Behavior                                      | HTTP Status |
|----------------------------|-----------------------------------------------|-------------|
| No user profile            | `"User not found"`                            | 404         |
| No current occupation set  | `"User has no current occupation set"`         | 400         |
| No skill ratings submitted | `"User has no skill ratings"`                  | 400         |
| Partial skill ratings      | Unrated skills default to rating 0 (capability 0.0) | 200   |

There is **no guided onboarding flow** that steers users through the required setup steps. The API returns hard errors until the user has completed all three prerequisite steps (profile, current occupation, skill ratings).

### 3.2 System Cold Start

| Condition                    | Behavior                                           | HTTP Status |
|------------------------------|-----------------------------------------------------|-------------|
| No cached occupations        | `"No occupations in cache. Run cache warming first."` | 503       |
| Calibration model not trained| Falls back to baseline (v1) scoring                 | 200         |
| < 50 feedback samples        | Training task returns `"skipped"` with reason       | N/A (task)  |

### 3.3 Occupation Cold Start

- **Rare occupations:** No special handling. Scored identically to popular occupations with the same skill profile.
- **Missing skill data:** Occupations with no cached skills are silently skipped during scoring (the `if not occupation_skills: continue` guard in the endpoint).
- **Unseen skill combinations:** No detection mechanism. Novel combinations of rated skills are passed to the scorer without any uncertainty quantification.

### 3.4 Calibration Model Cold Start

The transition from v1 (baseline) to v2 (calibrated) requires:
1. At least 50 feedback records with actionable signals (HIDE/APPLY/INTERVIEW/OFFER).
2. Manual activation of the trained model (the `is_active` flag on `ModelRegistry` defaults to `False`).
3. Even when a calibration model exists, the recommendation endpoint does not currently use it for scoring.

## 4. Technical Debt

### 4.1 Critical

#### TD-1: Sync-in-Async Event Loop Conflict

**Location:** `app/tasks/tasks.py`, lines 63, 84, 304
**Issue:** `asyncio.run()` is called inside synchronous Celery tasks (`warm_occupation_cache`, `search_and_cache_occupations`). If Celery ever runs in an environment with an existing event loop (e.g., behind an async worker or during testing), `asyncio.run()` will raise `RuntimeError: This event loop is already running`.
**Impact:** Cache warming and search tasks may fail silently in certain deployment configurations.
**Recommendation:** Use `asyncio.new_event_loop()` with explicit cleanup, or refactor the O\*NET client to support synchronous calls.

#### TD-2: Hardcoded Feature Placeholders in Training Task

**Location:** `app/tasks/tasks.py`, lines 225-227
**Issue:** Three calibration features are hardcoded:
```python
"mean_rating": 2.0,       # Placeholder
"rating_variance": 1.0,   # Placeholder
"num_rated_skills": 10,   # Placeholder
```
**Impact:** The calibration model trains on fabricated user-level features. The coefficients learned for `mean_rating`, `rating_variance`, and `num_rated_skills` will be meaningless. This contaminates the model's ability to learn user confidence patterns and reduces effective feature dimensionality from 9 to 6.
**Recommendation:** Query actual user skill ratings from `user_skill_rating` table during training data preparation.

#### TD-3: Missing `gap_weight` in Persisted `score_json`

**Location:** `app/api/endpoints.py`, lines 539-546
**Issue:** When `score_json` is persisted to `recommended_occupation`, `gap_weight` is omitted from the `top_gaps` entries:
```python
"top_gaps": [
    {
        "element_id": g.element_id,
        "skill_name": g.skill_name,
        "required_importance": g.required_importance,
        "user_capability": g.user_capability,
        # gap_weight is missing
    }
    for g in score.top_gaps[:5]
]
```
The training task then computes `sum_missing_weights` by summing `gap.get("gap_weight", 0)` from these stored top\_gaps, which always yields 0. This makes the `sum_missing_weights` feature constant across all training samples, rendering it useless.
**Recommendation:** Include `gap_weight` in the persisted `score_json` top\_gaps structure.

### 4.2 High

#### TD-4: Calibration Model Not Wired Into Endpoint

**Location:** `app/api/endpoints.py`, line 465
**Issue:** The `RecommendationRequest` schema accepts `use_calibration` and `enable_exploration` flags, and the endpoint imports `CalibrationModel` and `ExplorationPolicy`, but the scoring loop exclusively uses `get_baseline_scorer()`. The calibration model is never loaded or applied.
**Impact:** Users cannot benefit from learned calibration even after a model is trained and activated.
**Recommendation:** Implement the calibration reranking path in the recommendation endpoint when `use_calibration=True` and an active model exists.

#### TD-5: TRAINABLE Bucket Uses OR Logic

**Location:** `app/ml/scoring.py`, lines 246-252
**Issue:** The TRAINABLE bucket condition is:
```python
if trainable_match_min <= match_score <= trainable_match_max
   or trainable_gap_min <= gap_severity <= trainable_gap_max:
```
This means an occupation with `match_score=10` and `gap_severity=30` is classified as TRAINABLE (the gap condition alone qualifies it), even though the extremely low match score suggests it should be LONG\_RESKILL.
**Impact:** Users may see occupations labeled "Trainable" that are realistically out of reach. Conversely, some occupations that satisfy only the match condition but have very high gap severity would also be labeled TRAINABLE.
**Recommendation:** Consider using AND logic, or add a secondary guard (e.g., `match_score >= 30` minimum for the gap-only path).

#### TD-6: All Occupations Loaded and Scored

**Location:** `app/api/endpoints.py`, lines 455-459
**Issue:** The recommendation endpoint fetches every occupation in the cache with a full eager load of skills:
```python
result = await db.execute(
    select(Occupation)
    .options(joinedload(Occupation.occupation_skills).joinedload(OccupationSkill.skill))
)
```
**Impact:** As the occupation cache grows, this becomes an O(N) memory and compute bottleneck. With the full O\*NET database (~1,000+ occupations, each with 10-35 skills), this could cause significant latency.
**Recommendation:** Implement pre-filtering (e.g., by job zone similarity, skill overlap) or pagination to limit the candidate set before scoring.

### 4.3 Medium

#### TD-7: No Model Versioning Beyond Registry Table

**Location:** `app/models/models.py`, `ModelRegistry` class
**Issue:** The `model_registry` table tracks model metadata and an `artifact_path`, but there is no:
- Artifact storage abstraction (paths are local filesystem)
- Version comparison or rollback mechanism
- Shadow/canary deployment support
- Automated promotion from `is_active=False` to `True`
**Recommendation:** Add a model lifecycle API and consider cloud-backed artifact storage (e.g., S3).

#### TD-8: No A/B Testing Infrastructure

**Issue:** There is no mechanism to split traffic between model versions. The `model_version` is logged per event, but all users see the same model.
**Recommendation:** Implement experiment assignment at the user level and track conversion metrics per variant.

#### TD-9: No Calibration Monitoring or Drift Detection

**Issue:** Once a calibration model is trained, there is no:
- Scheduled evaluation against held-out data
- Feature distribution monitoring
- Prediction drift alerting
- Automatic retraining triggers
**Recommendation:** Add a periodic evaluation task that compares recent prediction accuracy against training metrics and alerts on degradation.

#### TD-10: No Occupation Clustering for Rare Occupations

**Issue:** Occupations with few or no feedback samples get the same treatment as well-represented ones. The calibration model has no mechanism to borrow strength from similar occupations.
**Recommendation:** Implement SOC code hierarchy grouping or skill-profile clustering to enable transfer learning for rare occupations.

#### TD-11: Boundary Gap Between READY\_NOW and TRAINABLE

**Location:** `app/ml/scoring.py` and `tests/unit/test_scoring.py`, line 254
**Issue:** There is a gap in the bucket logic. A score of `match_score=74.9, gap_severity=25.0` is:
- Not READY\_NOW (match < 75)
- Not TRAINABLE (match > 74.0 **and** gap < 26.0)
- Therefore: LONG\_RESKILL

This means a user with a 74.9% match and only 25% gap severity is told they need "significant reskilling" -- a clearly incorrect classification. The test at line 254 of `test_scoring.py` explicitly asserts this surprising behavior.
**Impact:** Users near the READY\_NOW boundary receive discouraging guidance.
**Recommendation:** Close the gap by adjusting thresholds (e.g., `trainable_match_max=74.9`) or changing TRAINABLE upper bound to be exclusive of READY\_NOW lower bound rather than leaving a gap.

### 4.4 Low

#### TD-12: Top Gaps Truncation Inconsistency

**Issue:** The scorer returns the top 10 gaps (`top_gaps[:10]` in `score_occupation`), but the endpoint truncates to 5 when storing in `score_json` and when building the API response. The calibration training task reads from `score_json`, so it only sees at most 5 gaps.
**Recommendation:** Standardize on a single truncation point, or store all gaps and truncate only in the API response.

#### TD-13: `score_json` Metadata Does Not Include `sum_missing_weights`

**Issue:** The `metadata` dict in `score_json` contains `skills_with_gaps` (count) and `job_zone_diff`, but not `sum_missing_weights`. The training task attempts to reconstruct this from `top_gaps[].gap_weight` (which is missing, see TD-3).
**Recommendation:** Compute and store `sum_missing_weights` directly in the score metadata.

#### TD-14: No Input Validation on Skill Rating Element IDs

**Issue:** The `UserSkillRatingsRequest` accepts any string as `element_id`. There is no validation that the element ID corresponds to a known O\*NET skill in the `skill` table.
**Recommendation:** Add foreign key validation or at least a warning when unknown element IDs are submitted.

#### TD-15: ExplorationPolicy Selects by Position, Not Uncertainty

**Location:** `app/ml/calibration.py`, lines 350-373
**Issue:** The `select_exploration_items` method picks items from the middle of the ranked list rather than selecting items with high prediction uncertainty (e.g., predicted probability near 0.5).
**Recommendation:** If exploration is implemented, select items where `|predicted_probability - 0.5|` is minimized.

## 5. Summary of Findings

### By Severity

| Severity | Count | IDs                           |
|----------|-------|-------------------------------|
| Critical | 3     | TD-1, TD-2, TD-3              |
| High     | 3     | TD-4, TD-5, TD-6              |
| Medium   | 4     | TD-7, TD-8, TD-9, TD-10       |
| Low      | 5     | TD-11, TD-12, TD-13, TD-14, TD-15 |

### Top 5 Recommended Actions

1. **Fix hardcoded feature placeholders (TD-2):** Query actual user ratings during training data extraction. This is a data correctness issue that invalidates any trained calibration model.

2. **Persist `gap_weight` in `score_json` (TD-3):** Without this, `sum_missing_weights` is always zero in training data, making the feature useless and potentially misleading the model.

3. **Wire calibration model into the endpoint (TD-4):** The calibration model infrastructure exists but is disconnected from the serving path. Complete the integration to enable learned reranking.

4. **Fix the sync-in-async pattern (TD-1):** Replace `asyncio.run()` with proper event loop management in Celery tasks to prevent runtime failures in production deployments.

5. **Close the READY\_NOW/TRAINABLE boundary gap (TD-5, TD-11):** Revise bucket logic to eliminate the dead zone where near-ready users are classified as LONG\_RESKILL, and reconsider the OR logic for the TRAINABLE bucket.
